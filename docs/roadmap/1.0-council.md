# 玄玑 1.0 路线图 · 议会式群英会（Council + Judge）

> 状态：规划中。0.9.0 收尾后启动；预计跨 0.10 / 0.11 两个小版本完工，1.0 释出。

## 为什么需要议会式？

监督式（Supervisor）是默认拓扑——主 Conductor 持完整上下文，按需召唤 sub-agent 跑专项。
适合 90% 场景，因为：

- 上下文集中，token 不浪费
- 决策权清晰：Supervisor 综合，sub-agent 只贡献片段
- audit / gate 链路自然覆盖（sub-agent 召唤就是一次工具调用）

但有 3 类场景监督式做不好：

1. **架构选型类决策**：QBCore vs QBox vs ESX 选哪个？这种问题没有"一个正确答案"，
   不同 sub-agent 用不同视角并行论证比 Supervisor 一个人想全面更可靠
2. **跨多个文件的安全/合规审计**：>10 文件改动的安全分析，单个 sub-agent
   的注意力会失焦，多 reviewer 独立扫一遍再合议更稳
3. **跨家模型一致性校验**：让 Sonnet / GPT-5.5 / DeepSeek 各自给一份方案，
   差异就是真问题——共同认可的部分往往是对的

议会式（Council）就是为这三类场景准备的"重型武器"。日常用监督式就好。

## 设计核心

### 拓扑

```
                    ┌─ Councilor #1（Sonnet · 稷下生）─┐
                    │                                  │
小宝问题 → 议会发起 ─┼─ Councilor #2（GPT-5.5 · 司鉴）─┼─→ Judge → 裁决书 → 项目记忆
                    │                                  │
                    └─ Councilor #N（DeepSeek · 百工匠）┘
                          （并行独立跑，不互相看输出）
```

关键约束：

- **并行** —— 用 `asyncio.gather` 同时跑，省时间
- **独立** —— Councilor 之间不共享任何中间状态（不知道彼此存在）
- **异构鼓励** —— 同一角色配不同 profile，或同一 profile 配不同角色
- **Judge 必须用旗舰** —— 默认 active profile 的 default_model；如果配了 anthropic profile，强制用 Opus
- **裁决写记忆** —— 裁决书自动写入 `project` scope 的 `episodic` 记忆，作为决策档案

### Councilor

复用 0.3 起的 `SubAgent`——每个 Councilor 就是一个 sub-agent，只是被批量调度。
角色 / 工具白名单 / 模型偏好等参数一致。

新引入 `CouncilSpec`：

```python
class CouncilSpec(BaseModel):
    question: str                    # 议题，所有 Councilor 共享
    councilors: list[CouncilorSpec]  # 至少 2 名，建议奇数避免平局
    judge: JudgeSpec
    deadline_seconds: float = 120.0  # 总超时


class CouncilorSpec(BaseModel):
    role: str                        # 中文正名或英文别名
    profile_override: str | None     # 跨家拉异构
    model_override: str | None       # 同 profile 内换 model
    brief_extra: str = ""            # 给该 Councilor 的额外提示
```

### Judge

新引入 `Judge`——结构化的裁决器，**不是普通 sub-agent**：

- 输入是结构化数据（议题 + N 份 Councilor 输出）
- 输出固定 schema 的 `Verdict`（不是自由文本）
- 默认走 active profile 的 default_model；anthropic profile 时强制 Opus
- system prompt 固化在 `xuanji/ensemble/judge.py`

```python
class Verdict(BaseModel):
    summary: str                     # 一段话：议会得出什么结论
    chosen_path: str | None          # 选了哪个方案（可空，如全部都不行）
    consensus_points: list[str]      # 各 Councilor 共识的点
    divergence_points: list[str]     # 分歧的点 + 各方原因
    risks: list[str]                 # Judge 看到的风险
    decided_by: str                  # judge model id
    councilors: list[str]            # 参与的 Councilor model id 列表
    decided_at: float                # 时间戳
```

### 记忆固化

`Verdict` 自动写到 `project` scope 的 `episodic` 记忆，命名空间 `council_decisions`。
重要性按 `len(divergence_points) + 1` 加权——分歧越多、决策越重要、衰减越慢。

下次问类似问题时 reflux 会召回旧裁决书，避免重复议会。

### 入口

新增工具 `convene_council`（玄玑能调）和 CLI 命令 `xuanji council` 两条路径：

**LLM 工具调用**：

```python
# 玄玑发现要做大决策时主动召集
{
    "name": "convene_council",
    "args": {
        "question": "这个项目从 ESX 迁移到 QBox 的代价值得吗？",
        "councilor_roles": ["稷下生", "司鉴", "百工匠"],
        "use_heterogeneous": true   # 自动跨家分配 profile
    }
}
```

`convene_council` 默认 `RiskTag.IO`——会写记忆。司辰阁可配为 HITL 强制确认。

**CLI**：

```bash
xuanji council convene "ESX → QBox 迁移代价" \
    --role 稷下生 --role 司鉴 --role 百工匠 \
    --heterogeneous

xuanji council list                    # 看历史裁决书
xuanji council show <verdict_id>       # 看完整裁决书
xuanji council export <verdict_id>     # 导出 markdown 给小宝写文档用
```

## 风险与缓释

| 风险 | 缓释 |
|---|---|
| 议会成本失控（N 倍 token） | 默认 monitor budget，单次 Councilor 上限 4k 输出；超 1000 token 议题前必须 HITL 确认 |
| Judge 偏向某个 Councilor 风格 | Verdict schema 强制 `consensus_points` + `divergence_points` 两段，不允许 Judge 跳过分歧 |
| 异构 profile 用户没装多家时报错 | 单 profile 用户自动降级——同 profile 不同 system prompt 模拟"不同视角" |
| 旧裁决书过时反而误导 | reflux 时根据 `decided_at` + 项目当前状态做 freshness 评分，太老的不召回 |

## 现有基础设施复用

不新造轮子：

- `SubAgent` 类直接复用——Councilor 就是一个 sub-agent
- `ModelRouter` 复用——异构选 profile 走它
- `Memory` 复用——Verdict 写 episodic
- `Conductor` 不动——`convene_council` 是普通工具，落在主 tool loop 里
- audit / gate 链路自动覆盖

新增模块只有 `xuanji/ensemble/{council,judge}.py` + `xuanji/tools/council.py`。

## 与监督式的关系

```
日常对话       → 玄玑独立回答（无 ensemble）
专项任务       → dispatch_subagent（监督式，0.3 起）
高危 / 选型    → convene_council（议会式，1.0 新增）
```

监督式不被替代——它仍是 ensemble 的默认值。议会式只在玄玑判断"这事需要多视角并行"时
主动 propose，或小宝显式 `xuanji council convene` 时启用。
